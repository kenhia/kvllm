# kai — RTX 5090 hardware fault on GPC 9 (2026-08-21)

**Verdict: the GPU faults on basic CUDA work, ~50% of the time, always on the same
physical SM. This is a hardware fault, not a software problem.** It survives a reboot and a
full power-off. The card should be treated as failing pending a driver-variant test (below).

| | |
| --- | --- |
| Host | `kai` |
| GPU | NVIDIA GeForce RTX 5090, 32,607 MiB |
| UUID | `GPU-1c36fcbc-79f8-a696-7530-f4a73be8cd9b` |
| Driver | `595.58.03` (`nvidia-driver-595-**open**`, `595.58.03-0ubuntu0.24.04.1`) |
| CUDA | 13.2 (torch built against cu130, torch 2.13.0) |
| VBIOS | `98.02.2E.40.E0` |
| Board serial | `0` (reported by NVRM) |

## The evidence

### 1. Minimal reproduction — no vLLM, no model, no quantization

Five lines of PyTorch. Allocate 2 GiB of fp16 and fill it with random normals:

```python
import torch
n = int(2 * (1024**3) / 2)                       # 2 GiB of fp16
t = torch.empty(n, device="cuda", dtype=torch.float16)
torch.nn.init.normal_(t, 0.0, 0.02)
torch.cuda.synchronize()
print(t.float().mean().item())
```

Run 12 times, each in a **fresh process** (a CUDA fault poisons the context, so the process
must be discarded between trials):

```
 1 ok    2 ok    3 FAIL   4 ok    5 ok    6 ok
 7 FAIL  8 ok    9 FAIL  10 FAIL 11 FAIL 12 FAIL
--- 2 GiB normal_ x12:  ok=6  fail=6  hang=0 ---
```

**6/12 failures on identical work.** The failure is
`torch.AcceleratorError: CUDA error: an illegal memory access was encountered`
(`cudaErrorIllegalAddress`). Note the clustering in trials 9–12 — it appears to worsen with
accumulated use or thermal load within a session.

### 2. It is not size-dependent — it is random

| allocation | result |
| --- | --- |
| 0.25 GiB | OK |
| 0.50 GiB | **FAIL** (illegal address) |
| 1.00 GiB | **HANG** (killed at 120 s) |
| 2.00 GiB | OK |
| 4.00 GiB | OK |

A separate 0.41 GiB compute test (20× 8192³ bf16 matmul) passed in 0.21 s with a correct
checksum. So the card is not dead and small/short work often succeeds — which is exactly why
this masqueraded as an intermittent software bug for hours.


This is the whole case, and it is worth reading closely:

- **Every MMU fault is on `GPC9`** — Graphics Processing Cluster 9, same client
  (`GPCCLIENT_T1_9`) each time.
- **Every SM warp exception is on the identical SM: `GPC 9, TPC 4, SM 1`.**
- The `Xid 13` ESR registers are **byte-identical** across two events 7 minutes apart
  (`0x5997a8=0x1c81fb60`, `0x5997ac=0x1174`); only one bit differs in `ESR 0x5997b0`
  (`0x108000e` vs `0x10c000e`).
- The faulting **virtual addresses differ wildly** between events (`0x0_000ff000`,
  `0xffcc50b8_58c03000`, `0x79dc_b3000000`) — so it is not one bad buffer or one bad
  pointer in one program.
- The faults come from **different processes** (`VLLM::EngineCor`, bare `python3`) running
  **entirely different workloads** (a vLLM model load; a five-line tensor fill).

Different programs, different workloads, different addresses, **same SM**. That is the
signature of defective silicon in one SM, not of a software bug.

Xid meanings: **13** = graphics engine exception (here, an SM executing an out-of-range
address); **31** = GPU memory page fault, usually an illegal access by a kernel; **43** =
the channel being torn down as a consequence.

### 4. It survives power cycling

The card was rebooted once and fully powered off once. A cold power-off clears GSP state,
driver state and all volatile GPU state. The fault returned both times. Earlier in the
sequence `nvidia-smi` also reported `ERR!` for fan/temp/power and
`Channel Repair Pending: GPU requires reset`; that flag has since cleared on its own and
currently reads `No`, and the card idles normally at ~13 W / 41 °C.

## What this invalidates

**The "vLLM 0.27.1 Gated DeltaNet bug" diagnosed earlier on 2026-08-20 is almost certainly
not a vLLM bug.** The `CUDA illegal memory access` traced to
`vllm/model_executor/layers/mamba/gdn/qwen_gdn_linear_attn.py:1058` in
`_warmup_prefill_kernels` was this hardware faulting; that kernel merely happened to be
resident when the bad SM was scheduled. The accompanying silent hangs (engine spinning at
100% GPU, zero requests in flight, token counters frozen) are the same fault in its
non-fatal form.

`gemma-4-31b-it-awq` — a different model, different architecture, different quantization —
fails with the identical error, faulting inside `torch.nn.init.normal_` during weight
initialisation. That was the clue that should have ended the software theory sooner.

**The methodological lesson:** the project's prime rule is "when a score looks wrong, audit
the harness before blaming the model." This incident adds a rung *below* the harness. A
plausible, well-localised software explanation — a real file and line number in a real
upstream kernel — is not evidence that the cause is software. The moment a **second,
unrelated** model failed the same way, the correct next step was a bare-metal reproduction
(five lines of PyTorch, no project code), not more investigation inside the stack. That
would have reached this conclusion in minutes rather than hours.

## What still stands

The **`reasoning_effort: xhigh`** finding is independent of the hardware and remains valid.
Qwen3.8's chat template defaults `reasoning_effort` to `xhigh`; against the judged/vision
suites' 4096-token budget the model spends the entire budget inside `<think>` and returns an
empty answer that the judge correctly scores 0. That is reproducible arithmetic about token
budgets, evidenced by `stop_reason: max_tokens` at exactly `output_tokens: 4096`, and it has
nothing to do with a faulting SM.

## Suggested next steps

1. **Test the driver variant before concluding hardware.** The installed driver is the
   **open** kernel module (`nvidia-driver-595-open`). Switching to the proprietary module of
   the same version is the cheapest experiment that could still exonerate the card:

   ```sh
   sudo apt install nvidia-driver-595   # proprietary module, same 595.58.03
   sudo reboot
   ```

   Then re-run the 12-trial reproduction above. A fault pinned to one SM across power cycles
   points hard at the die, so expect this to fail too — but it is cheap and it is the one
   remaining software variable.

2. **If it still fails, RMA the card.** The Xid 13 / GPC 9 / TPC 4 / SM 1 evidence with a
   five-line reproduction is a strong warranty case. Capture
   `journalctl -k | grep NVRM` and the trial output.

3. **Do not run evals on this card until it is resolved.** Any number it produces is
   suspect — a fault that corrupts a weight fill or an attention kernel can also silently
   corrupt an output that never throws. Results already gathered on 2026-08-20 should be
   treated as unreliable.

4. `kvllm.service` is currently **stopped and disabled** so the card is not pegged on boot.
   Re-enable when the hardware is trusted again:

   ```sh
   systemctl --user enable --now kvllm
   ```
